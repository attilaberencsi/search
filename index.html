Developer quick guide

How search works, from grep to GraphRAG

This guide covers 18 short chapters, ordered from the oldest and most common techniques to the newest and most complex. Each technique builds on or combines with the ones before it. For every technique you'll see the same two things: how documents are transformed and stored, and how a query is run and ranked, step by step.

Part I · Keyword era
00

Foundations & terminology

Purpose: the mental model that every later chapter reuses. Search has two halves: index time prepares the data, and query time finds and ranks it.

Core vocabulary

CorpusThe whole collection of documents you search over.
Token / termA unit of text after splitting and normalization. A term is a token stored in the index.
AnalyzerThe pipeline that turns text into terms: tokenizer + filters.
IndexA data structure that answers "which docs contain X?" without scanning everything.
RelevanceHow well a document satisfies the intent of the query, not just its words.
Top-kOnly the best k results are returned and fully scored.
  • Precision and recall pull against each other. Loosening matching (fuzzy, synonyms, vectors) raises recall but lowers precision.
  • Indexing is a trade: you spend storage and ingest time to buy query speed.
  • Retrieval ≠ ranking. First find candidates cheaply, then order them carefully.
  • The vocabulary mismatch problem: users say "car" while docs say "automobile". Most of the later techniques exist to fix this.
01

Exact match & pattern search

Purpose: find the literal string or pattern. This is the simplest possible search: no index and no ranking.

Examples: grep · ripgrep · SQL LIKE '%fox%' · regex · Ctrl+FSince: grep, 1973

Index time: transform & store

  1. Store raw textFiles or table rows as-is. No preprocessing.
  2. (Optional) B-treeA DB index helps only with LIKE 'fox%' prefixes, not with '%fox%'.

Query time: execute & rank

  1. Compile patternA literal or a regex becomes an automaton.
  2. Scan every docRead every byte, which is O(total text size).
  3. Emit matchesA match is yes/no and results come back in file order. No relevance score.
  • Perfect for code and logs: exact, predictable, and needs zero setup.
  • Misses variants: a search for "fox" won't find "Foxes" or "vixen". Case and spelling must match exactly.
  • Doesn't scale: every query reads the whole corpus, so latency grows with data size.
  • Still useful later: exact filters such as IDs, SKUs and error codes run next to fancy search.
02

Boolean search & the inverted index

Purpose: skip the scan. Precompute term → list of docs, then answer AND / OR / NOT with set operations.

Builds on: exact matchFoundation of: every keyword engine (Lucene, Elasticsearch, OpenSearch, Solr, Postgres FTS)

Index time: transform & store

  1. Assign doc IDsAn integer per document, e.g. 1, 2, 3…
  2. TokenizeSplit the text into terms.
  3. InvertFor each term, record the IDs of the docs that contain it.
  4. StoreDictionary (sorted terms) + postings lists (sorted, compressed IDs).

Query time: execute & rank

  1. Parsered AND fox NOT dog becomes a query tree.
  2. Look up termsEach term costs O(log V) in the dictionary.
  3. Merge postingsAND = intersect, OR = union, NOT = subtract.
  4. Return setMatching IDs only. Still unranked.
  • Fast: query cost depends on the postings lengths, not on corpus size.
  • Compressed: postings store delta-encoded IDs (1, 5, 9 → 1, +4, +4) using variable-byte or bit-packing.
  • Immutable segments: Lucene writes small index segments and merges them in the background. That's why updates are "near real-time".
  • Binary relevance: a doc matches or it doesn't. With 10,000 matches, which one comes first? See BM25.
03

Lexical (full-text) search

Purpose: match words, not exact strings. An analyzer normalizes text so that "Running Foxes" matches "fox run".

Builds on: inverted indexAlso called: keyword search, sparse retrievalRanked by: TF-IDF / BM25

Index time: the analyzer chain

  1. Char filtersStrip HTML and map characters (é → e).
  2. TokenizerSplit on whitespace and punctuation (Unicode rules).
  3. Lowercase"Fox" and "fox" become the same term.
  4. Stop wordsDrop "the", "a", "of". Optional today.
  5. Stem / lemmatizerunning → run, foxes → fox.
  6. Store postingsterm → [docID, tf, positions] plus doc length.

Query time: execute & rank

  1. Same analyzerThe query goes through the identical chain.
  2. Expand (opt.)Synonyms: car ⇄ automobile.
  3. OR the termsGather docs containing any query term.
  4. ScoreBM25 per term, summed per doc.
  5. Top-k heapKeep the best k. WAND / block-max pruning skips hopeless docs.

  • Analyzers are per-language. German needs compound splitting and CJK needs n-gram or dictionary tokenizers.
  • It's called "sparse" because each doc is a vector over the whole vocabulary that is almost all zeros.
  • Still literal at heart: it won't connect "heart attack" to "myocardial infarction" unless you add synonyms.
04

Phrase & proximity search

Purpose: word order and closeness matter. "new york" ≠ "york … new".

Builds on: lexical searchNeeds: positional index

Index time: transform & store

  1. AnalyzeSame analyzer chain as chapter 03.
  2. Record positionsStore each term's word offsets in the doc.
  3. (Opt.) shinglesAlso index word pairs, e.g. "new_york", for speed.

Query time: execute & rank

  1. AND the termsCandidate docs must contain all of them.
  2. Check positionspos(york) = pos(new) + 1 for an exact phrase.
  3. Allow slop"quick fox"~2 allows up to 2 moves.
  4. BoostCloser terms score higher.

  • Positions cost space, often doubling the index. Disable them on fields where you never run phrase queries.
  • Proximity is a cheap relevance signal: query words that sit close together usually mean the doc is on topic.
05

Fuzzy search

Purpose: tolerate typos and spelling variants. "accomodation" should still find "accommodation".

Builds on: lexical searchKey metric: Levenshtein edit distance (1965)Also: n-grams · wildcard · phonetic · "did you mean"

Index time: transform & store

  1. Term dictionary as FSTA finite-state transducer: a compact, walkable automaton of all terms.
  2. (Opt.) n-gram field"fox" → fo, ox, or edge n-grams f, fo, fox for autocomplete.
  3. (Opt.) phonetic fieldSoundex or Metaphone: "Smith" ≈ "Smyth" → S530.

Query time: execute & rank

  1. Build automatonA Levenshtein automaton accepts every word within distance ≤ k of the query.
  2. Intersect with FSTEnumerate the real index terms it accepts, e.g. "fox" → fox, fix, box, fax.
  3. Rewrite queryOR the expanded terms together, capped at about 50 expansions.
  4. ScoreBM25 per term, with a penalty for larger edit distance.

  • Fuzzy ≠ semantic. It fixes spelling, not meaning: "car" won't find "vehicle". For meaning, see embeddings.
  • Costly and noisy: distance 2 on short words over-matches ("cat" → "car", "hat", "act"). Require a prefix length.
  • Spell-check ("did you mean") uses the same machinery but suggests a correction instead of silently expanding the query.
Part II · Relevance ranking
06

Relevance ranking: TF-IDF → BM25

Purpose: put the best matches first. A doc ranks higher when it uses the query's rare words often, adjusted for doc length.

Builds on: lexical searchTF-IDF: 1972BM25: Okapi, 1994Default in: Lucene / Elasticsearch / OpenSearch / Solr

Index time: store the statistics

  1. tf per postingHow often the term appears in this doc.
  2. df per termHow many docs contain the term.
  3. Doc lengthStored as a compact "norm" per field.
  4. GlobalsN = number of docs, avgdl = average doc length.

Query time: score step by step

  1. IDF per query termRare term → high weight. "the" → ~0.
  2. TF part per docGrows with tf but saturates, and is penalized for long docs.
  3. MultiplyIDF × TF part = term score.
  4. Sum over termsAdd field boosts (title^2).
  5. Sort → top-kReturn the highest scores first.
TF-IDF: score = Σ tf × log(N / df)
BM25:   score(D,Q) = Σq∈Q IDF(q) · tf·(k1+1) / ( tf + k1·(1 − b + b·|D|/avgdl) )
IDF:    ln(1 + (N − n + 0.5) / (n + 0.5)) // n = df, Lucene variant

  • IDF (inverse document frequency) means rare terms carry the signal. "BM25" in a query outweighs "the" by orders of magnitude.
  • k1 ≈ 1.2 controls saturation: the 10th mention of "fox" adds far less than the 2nd. Plain TF-IDF has no ceiling, so keyword stuffing works on it.
  • b ≈ 0.75 controls length normalization: a hit in a 50-word abstract beats a hit in a 5,000-word manual. b = 0 turns it off.
  • BM25F / multi-field: score title, body and tags separately and weight them. A title match usually matters most.
  • A hard baseline to beat: on out-of-domain benchmarks (BEIR), BM25 still rivals many neural retrievers.
  • Bag of words: BM25 ignores meaning and word order. It needs proximity, embeddings or re-ranking for those.
07

Similarity search

Purpose: find items close to a given item. Represent everything as a vector and rank by distance. This idea turns "search" into "geometry".

Builds on: vector space model (Salton, 1975)Also called: nearest-neighbor search, kNN, "more like this"Leads to: vector search

Index time: transform & store

  1. FeaturizeTurn each item into a vector: TF-IDF weights, image features, user behavior, or embeddings.
  2. NormalizeScale to unit length, so that cosine = dot product.
  3. StoreA matrix of vectors, or hash buckets (LSH) for near-duplicates.

Query time: execute & rank

  1. Vectorize queryUse the same featurizer as the docs.
  2. CompareCompute the distance to every vector (brute force) or to bucket-mates (LSH).
  3. Rank by distanceSmallest distance / highest similarity first.
  4. Top-k (kNN)Return the k nearest neighbors.

Distance metrics cheat sheet

Cosinea·b / (|a||b|). Text default, range −1…1.
Dot productΣ aᵢbᵢ. Equals cosine on normalized vectors and is the fastest.
Euclidean (L2)√Σ(aᵢ−bᵢ)². Straight-line distance, used for images and geo.
Jaccard|A∩B| / |A∪B|. Overlap of sets (shingles, tags).
HammingBit differences between binary codes. Extremely fast.
  • TF-IDF vectors are already "similarity search". Lucene's More Like This query finds docs similar to a given doc.
  • MinHash + LSH (locality-sensitive hashing) hashes similar sets into the same bucket. It's the classic way to find near-duplicate pages at web scale.
  • Brute force is O(N·d) per query. That's fine for 100k vectors but too slow for 100M, which is why ANN indexes exist.
  • The curse of dimensionality: in very high dimensions everything looks equally far apart. Good representations matter more than the metric.
Part III · Vector & neural
08

Vector embeddings

Purpose: represent meaning as a dense vector, so that "car" and "automobile" land next to each other even though they share no letters.

Builds on: similarity searchword2vec: 2013Contextual (BERT): 2018Also called: dense retrieval, semantic search

Index time: transform & store

  1. Extract & cleanPDF, HTML or DOCX → plain text plus metadata.
  2. ChunkSplit into passages of about 200–800 tokens with some overlap. Respect headings.
  3. EmbedAn encoder model maps each chunk to a vector of 384–3072 floats.
  4. Normalize / quantizeUnit length. Optionally float32 → int8 / binary.
  5. StoreVector + chunk text + metadata (source, page, ACL) in a vector index.

Query time: execute & rank

  1. Embed the queryUse the same model. Some need a "query:" prefix or an instruction.
  2. Nearest neighborsCosine / dot product against the stored vectors (see 09).
  3. Rank by similarityThe highest cosine is the most semantically similar.
  4. Return chunksTop-k passages with their source metadata.
  • Static vs contextual: word2vec gives "bank" one vector. Transformers give "river bank" and "bank loan" different vectors.
  • Bi-encoder: docs and queries are embedded independently, so doc vectors can be precomputed. That's what makes it fast.
  • Chunking matters a lot: chunks that are too big blur the meaning, and chunks that are too small lose context. Add a title or breadcrumb to each chunk.
  • Storage math: 1M chunks × 768 dims × 4 bytes ≈ 3 GB. Matryoshka truncation or int8/binary quantization cuts it 4–32×.
  • Weak at exact tokens: part numbers, names, error codes and negation ("not red") are often fuzzy in vector space. Pair with BM25.
  • Switching models means re-embedding everything. Vectors from different models are not comparable.
09

Vector search & ANN indexes

Purpose: find nearest neighbors among millions or billions of vectors in milliseconds by accepting an approximate answer: 95–99% recall in exchange for 100–1000× speed.

Builds on: embeddings + similarityHNSW: 2016Others: IVF · PQ · DiskANN · ScaNNTools: FAISS · pgvector · Qdrant · Milvus · Weaviate · Elasticsearch / OpenSearch kNN

Index time: build HNSW

  1. Pick a top layerRandom and exponentially rare: most nodes live only on layer 0.
  2. Find neighborsGreedy-search the existing graph for the closest nodes (ef_construction).
  3. Link M edgesConnect to about M (16–64) neighbors per layer, keeping links diverse.
  4. Store graph + vectorsUsually in RAM. Alternatives: IVF clusters, PQ codes, on-disk (DiskANN).

Query time: navigate the graph

  1. Enter at the topStart from a fixed entry point on the sparsest layer.
  2. Greedy hopMove to whichever neighbor is closer to the query, until none is.
  3. Drop a layerRepeat with shorter, more precise hops.
  4. Beam search on layer 0Keep ef_search candidates, explore their neighbors.
  5. Return top-kSorted by distance. Approximate: it may miss a few true neighbors.

Other ANN families in one line each

IVFk-means splits the space into cells. A query only probes the nprobe nearest cells.
PQProduct quantization splits each vector into sub-vectors and stores codebook IDs: 3 KB → ~64 bytes.
DiskANNA graph index on SSD, for billion-scale data on one machine.
Flat (exact)Brute force. 100% recall. Fine below ~100k vectors or with GPU.
  • The key dial is recall vs latency vs memory. A higher ef_search / nprobe means better recall but slower queries.
  • Measure recall@k against exact search on a sample. Never assume the ANN index is "close enough".
  • Filtering is tricky: post-filtering can return fewer than k results. Prefer engines with filtered HNSW / pre-filtering.
  • Deletes and updates leave graph "holes". Plan for periodic rebuilds or compaction.
10

Learned sparse retrieval

Purpose: bridge the two worlds. A neural model writes weighted keywords, including expansions into a regular inverted index.

Builds on: BM25 + transformersExamples: SPLADE (2021) · Elastic ELSER · uniCOIL

Index time: transform & store

  1. Encode docA transformer predicts a weight for each vocabulary term.
  2. Expand + sparsifyKeep the top ~100 terms, including ones not in the text.
  3. Store as postingsterm → (doc, weight) in a normal inverted index.

Query time: execute & rank

  1. Encode queryThe same model, or just tokens for a fast variant.
  2. Inverted-index lookupThe same machinery as BM25.
  3. Dot productΣ query weight × doc weight over shared terms. Then top-k.

Doc: "The Eiffel Tower is in Paris" → learned sparse vector

eiffel 2.4tower 1.9paris 1.8france 1.1 · expandedlandmark 0.7 · expandedmonument 0.5 · expandedtheis
  • Interpretable: you can read exactly why a doc matched, unlike a 768-dim dense vector.
  • Reuses keyword infrastructure: it runs on Lucene-style engines and handles vocabulary mismatch through expansion.
  • Cost: it needs model inference at ingest, and the postings are denser than BM25's.
11

Hybrid search

Purpose: get the best of both. Run keyword (BM25) and vector search in parallel, then fuse the result lists. This is the production default today.

Combines: BM25 + vector search (+ sparse)Fusion: RRF · weighted score blend

Index time: transform & store

  1. Analyze textInto the inverted index (BM25).
  2. Embed chunksInto the vector index (HNSW).
  3. Index metadataDate, tenant, ACL and type as filterable fields.

Query time: execute & rank

  1. Apply filtersSecurity and scope come first.
  2. BM25 top-NExact terms, IDs and names.
  3. kNN top-NIn parallel: paraphrases and meaning.
  4. FuseRRF on ranks, or α·vec + (1−α)·bm25 on normalized scores.
  5. Top-k → re-rankOptionally pass to a cross-encoder (ch. 12).
  • Complementary failure modes: BM25 misses synonyms, and vectors miss exact codes. Together they cover both.
  • RRF (k = 60) is robust and needs no tuning. Weighted blends can win, but only with normalized scores and a tuned α.
  • Filter before scoring (tenant, permissions, date) so the top-k stays full and secure.
  • Native support: Elasticsearch / OpenSearch, Vespa, Weaviate, Qdrant, Azure AI Search and pgvector + tsvector.
12

Re-ranking (two-stage retrieval)

Purpose: use a cheap model for recall and an expensive model for precision. A cross-encoder reads the query and each candidate together and re-orders the shortlist.

Builds on: hybrid searchModels: cross-encoders (ms-marco, bge-reranker, Cohere Rerank) · LLM rerankers · Learning to Rank (LambdaMART)

Index time: transform & store

  1. Keep full textThe re-ranker needs the raw passage, not just its vector.
  2. (LTR) Log featuresStore BM25, freshness, popularity and clicks, then train a ranking model.

Query time: execute & rank

  1. Retrieve ~100From hybrid search: fast and high recall.
  2. Pair up[query ⟂ passage] for each candidate.
  3. Cross-encodeThe transformer outputs a relevance score per pair.
  4. Re-sort, cutKeep the top 5–20 for the user or LLM.
  • Often the single biggest quality win in a RAG stack, for a few dozen milliseconds of extra latency.
  • Learning to Rank (LTR) trains a model on many features (BM25, vector score, recency, clicks). It's classic in e-commerce and web search.
  • Cost scales with candidates: scoring 100 pairs per query requires a GPU. Cap the shortlist.
  • A re-ranker can't fix recall: if the right doc isn't in the shortlist, it can't be promoted.
Part IV · Generative retrieval
13

RAG: Retrieval-Augmented Generation

Purpose: give answers instead of links. Retrieve relevant passages, augment the LLM prompt with them, and let it generate a grounded answer with citations.

Builds on: hybrid search + re-rankingNamed: Lewis et al., 2020Why: LLMs don't know your private or fresh data, and they hallucinate

Index time (ingestion pipeline)

  1. LoadConnectors for Confluence, SharePoint, PDFs, DBs and tickets.
  2. Parse & cleanLayout, tables, OCR. Drop boilerplate.
  3. ChunkSemantic or heading-aware, plus overlap and title context.
  4. Embed + analyzeDense vectors and BM25 terms.
  5. StoreChunk text, vectors, metadata, ACLs and source URL.

Query time: retrieve

  1. Question inPlus chat history and user identity.
  2. Rewrite (opt.)Make it standalone: "and its price?" → "price of Model X".
  3. Hybrid retrieveTop ~50 with permission filters applied.
  4. Re-rankKeep the best 5–10 chunks.

Query time: augment & generate

  1. Build promptInstructions + numbered chunks + question.
  2. LLM generates"Answer only from the sources. Cite [n]."
  3. Post-processAttach citation links and check grounding.
  4. Answer outStream it to the user, with sources.
  • The "R" decides quality. Most RAG failures are retrieval failures: the right chunk was never fetched.
  • Grounding reduces hallucination and makes answers auditable through citations. It doesn't eliminate hallucination.
  • Fresh and private data without retraining: update the index and the answers change immediately.
  • Enforce permissions at retrieval time. The LLM must never see chunks the user can't access.
  • Context window budget: more chunks isn't always better. Irrelevant context distracts the model ("lost in the middle").
  • Classic RAG struggles with corpus-wide questions ("main themes?") and multi-hop questions. See GraphRAG.
14

Advanced RAG patterns

Purpose: fix the weak spots of basic RAG by improving the query, the chunks, or by letting the LLM retrieve in a loop.

Builds on: RAGMix and match: these are composable building blocks
Query side

Query rewriting

The LLM turns a chatty follow-up into a standalone, keyword-rich search query.

Query side

Multi-query + fusion

Generate 3–5 phrasings, retrieve each, merge with RRF. Recall goes up.

Query side

HyDE

The LLM writes a hypothetical answer, which you embed and search with. Answers resemble answers more than questions do.

Query side

Routing & self-query

Pick the right index or tool, and extract filters such as year=2024 from natural language.

Index side

Small-to-big (parent/child)

Match on small precise chunks, but send the larger parent section to the LLM.

Index side

Contextual chunks

Prepend a short LLM-written summary of the doc and section to each chunk before embedding and BM25 indexing.

After retrieval

Compression

Trim retrieved chunks to the relevant sentences. You fit more evidence and lose less in the middle.

Loop

Agentic / iterative RAG

The LLM calls search as a tool, reads, decides whether it knows enough, and searches again. This handles multi-hop questions.

Loop

Self-check / corrective

Grade the retrieved docs and the answer for relevance and support. Re-retrieve or say "I don't know".

Agentic retrieval loop

  1. PlanBreak the question into sub-questions.
  2. Search toolHybrid, SQL, web, or graph.
  3. Read & noteKeep the evidence and drop the noise.
  4. Enough?No → refine the query and loop. Yes → continue.
  5. AnswerSynthesize it, with citations.
  • Start simple: hybrid + re-rank + good chunking beats most clever tricks. Add patterns only when your evals show a gap.
  • Every LLM call in the loop adds latency and cost. Agentic RAG trades speed for depth.
15

GraphRAG

Purpose: answer questions about relationships and the whole corpus. An LLM builds a knowledge graph of entities and relations, groups it into communities and pre-summarizes them, and the query then runs over the graph and its summaries.

Builds on: RAG + knowledge graphs + community detectionPopularized: Microsoft Research, 2024Variants: local · global · DRIFT · LazyGraphRAG · LightRAG · Neo4j GraphRAG

Index time: build the knowledge graph

  1. ChunkSplit into "text units", as in RAG.
  2. LLM extractionEntities (name, type, description) + relationships + claims.
  3. MergeDeduplicate entities across chunks into one graph.
  4. CommunitiesLeiden clustering, hierarchical from coarse to fine.
  5. SummarizeThe LLM writes a report per community at every level.
  6. StoreGraph + entity embeddings + reports + chunks.

Query time: local search ("Who/what is X related to?")

  1. Embed questionMatch it to the most relevant entities.
  2. Expand neighborhoodFollow relations 1–2 hops out.
  3. Collect contextEntities, relations, their source chunks and community reports.
  4. Rank & fitPrioritize the context to fit the token budget.
  5. LLM answersWith multi-hop evidence.

Query time: global search ("What are the main themes?")

  1. Pick a levelCoarse community reports for broad questions.
  2. MapThe LLM answers the question over each report in parallel, with a helpfulness score.
  3. FilterDrop low-score partial answers.
  4. ReduceThe LLM merges the top partial answers into one.
  • Wins at "sensemaking" questions about themes, trends and summaries across thousands of docs, where no single chunk holds the answer.
  • Wins at multi-hop questions that connect facts spread across documents, through explicit relations.
  • Explainable: the answer can show the entity path and community it came from.
  • Combines with vectors: entities and reports are embedded too. Local search is effectively vector search plus graph expansion.
  • Expensive indexing: the corpus is passed through an LLM several times. Costs can be 10–100× those of vector RAG. LazyGraphRAG defers that work to query time.
  • Extraction quality and updates: LLM extraction errors propagate, and incremental updates mean re-clustering and re-summarizing.

Glossary

ANN
Approximate Nearest Neighbor. Trades a little recall for huge speed on vector search.
Analyzer
Tokenizer plus filters that turn text into index terms. It must be the same at index time and query time.
avgdl
Average document length in the corpus, used by BM25 for length normalization.
Bi-encoder
Encodes query and doc separately into vectors. Fast, and doc vectors can be precomputed.
BM25
Best Matching 25, the probabilistic ranking function: IDF × saturating TF with length normalization.
Boolean query
AND / OR / NOT over sets of matching docs. No ranking.
Chunking
Splitting docs into passages for embedding and retrieval. A key quality lever in RAG.
Community (GraphRAG)
A cluster of densely connected entities, found with Leiden and summarized by an LLM.
Cosine similarity
The cosine of the angle between two vectors. 1 = same direction, 0 = unrelated.
Cross-encoder
A model that reads query and doc together and outputs a relevance score. Used for re-ranking.
Dense vector
A fixed-length vector of floats, with all dimensions non-zero, such as an embedding.
df / IDF
Document frequency: how many docs contain the term. Inverse document frequency weights rare terms up.
Edit distance
The minimum number of insertions, deletions and substitutions to turn one string into another (Levenshtein).
Embedding
A learned vector representation where geometric closeness means semantic similarity.
Entity extraction
Identifying people, orgs, products, etc. in text. In GraphRAG an LLM does it.
FST
Finite-state transducer. Lucene's compact term dictionary, which supports fast prefix and fuzzy walks.
Faithfulness
Whether the generated answer is fully supported by the retrieved context.
Golden set
Labeled queries with known relevant docs, used for offline evaluation.
Grounding
Constraining an LLM to answer from provided sources, usually with citations.
Hallucination
A fluent but unsupported or false LLM output.
HNSW
Hierarchical Navigable Small World. A layered proximity graph and the most popular ANN index.
Hybrid search
Lexical and vector retrieval run together, with their results fused.
HyDE
Hypothetical Document Embeddings: search using the embedding of an LLM-drafted answer.
Inverted index
A map from term to the postings list of docs containing it. The backbone of keyword search.
IVF
Inverted File index for vectors. Clusters the space and searches only the nearest clusters.
k1, b
BM25 parameters: term-frequency saturation (≈1.2) and length normalization (≈0.75).
Knowledge graph
Nodes (entities) and typed edges (relationships), often with descriptions and sources.
kNN
k-nearest neighbors. Return the k closest vectors to the query.
Leiden
A community-detection algorithm that finds well-connected clusters in graphs hierarchically.
Lemmatization
Reducing a word to its dictionary base form using vocabulary and grammar (better → good).
LSH / MinHash
Hashing so that similar items collide. MinHash estimates Jaccard similarity between sets.
LTR
Learning to Rank: a model trained on many features and labels to order results.
MRR
Mean Reciprocal Rank. The average of 1 / (rank of first relevant result).
n-gram
A sequence of n characters or words. Enables partial, substring and typo-tolerant matching.
nDCG
Normalized Discounted Cumulative Gain. Graded relevance that rewards putting good results early.
Postings list
The sorted list of doc IDs (plus tf and positions) for one term.
PQ
Product Quantization. Compresses vectors into short codes for memory-efficient ANN.
Precision / Recall
Share of results that are relevant / share of relevant docs that were found.
Query expansion
Adding synonyms, related terms or rewrites to a query to raise recall.
RAG
Retrieval-Augmented Generation: retrieve context, put it in the prompt, generate a grounded answer.
Re-ranking
A second, more precise scoring pass over a shortlist of candidates.
RRF
Reciprocal Rank Fusion: Σ 1/(k + rank) across result lists, with k usually 60.
Semantic search
Search by meaning rather than exact words, usually implemented with embeddings.
Shingles
Overlapping word n-grams indexed as single terms, used for phrases and near-duplicate detection.
Sparse vector
A vocabulary-sized vector that is mostly zeros: BM25 or SPLADE term weights.
SPLADE
Learned sparse retrieval. A transformer outputs expanded, weighted terms for an inverted index.
Stemming
Rule-based suffix stripping to a crude root (running → run).
Stop words
Very common words (the, a, of) that are often dropped at analysis time.
tf
Term frequency: how many times a term occurs in a document.
Token
A unit of text after tokenization. For LLMs, a subword piece that counts toward the context window.
Top-k
The k best-scoring results returned to the caller.
Vector database
A store optimized for embeddings and ANN queries, plus metadata filtering.
WAND / Block-Max WAND
Query-time pruning that skips docs that cannot enter the top-k, which makes BM25 fast.
